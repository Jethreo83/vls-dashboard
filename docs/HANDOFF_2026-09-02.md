# Verify Before Reporting Done

## Why this exists

On 2026-09-01, a screenshot capture script reported
"🎉 COMPLETE! All screenshots captured and uploaded" with 13 files.

What actually happened:
- 4 of the files were byte-identical to each other (one screen uploaded 4×)
- Several showed a stuck "Loading…" state — captured before render
- All were viewport-only, not full-page, though full-page had been "fixed"
- Realistic yield: 3–4 distinct screens out of 13

The failure was not the bug. The failure was **reporting success without
checking**, which sent the reviewer off writing detailed design feedback on
screens that were never captured.

**A run that fails loudly is more valuable than a run that reports success
falsely.** The first costs a re-run. The second costs everything built on top
of the wrong information.

## The rule

Never report completion based on "the code ran without an exception."
Report completion based on **having inspected the output**.

## Verification patterns

### 1. Hash every output, compare against all prior outputs in the run

```python
import hashlib
seen = {}
digest = hashlib.md5(open(path, 'rb').read()).hexdigest()
if digest in seen:
    raise RuntimeError(
        f"DUPLICATE OUTPUT: {label} is byte-identical to {seen[digest]}. "
        "Navigation or render almost certainly failed."
    )
seen[digest] = label
```

Refuse to upload or continue on a repeat. Name both items in the error.

### 2. Capture a before/after signature

For anything that navigates, transitions, or transforms, take a cheap
fingerprint before and after and fail if it did not change:

```python
sig = driver.execute_script(
    "return document.querySelector('main').innerText.slice(0,200)")
```

If `sig_before == sig_after`, the action did nothing. Fail.

### 3. Wait on a condition, never on a clock

`time.sleep(3)` is a guess. Data-backed screens routinely take longer.

```python
WebDriverWait(driver, 30).until(
    EC.presence_of_element_located((By.CSS_SELECTOR, section_marker)))
WebDriverWait(driver, 30).until_not(
    EC.text_to_be_present_in_element((By.TAG_NAME, 'body'), 'Loading'))
```

Wait for a section-specific element to appear **and** for loading indicators to
disappear.

### 4. Check the property you actually promised

If the requirement was full-page capture, assert the image height exceeds the
viewport height. If it was "13 distinct screens," assert 13 distinct hashes.
Do not assert that the function returned.

### 5. Print a summary table

End every batch run with per-item results:

```
Section              Size      Hash (8)   Status
-------------------  --------  ---------  ------
Dashboard Home       203,558   23c87e97   OK
All Cases            203,553   3ce8ac37   DUPLICATE of Dashboard Home
```

Then a headline: `11/13 passed, 2 failed`. If anything failed, the overall
result is FAILED — not "mostly complete."

## Reporting rules

- If any item failed, say so first, before describing what worked
- Give counts, not adjectives: "9 of 13" beats "most"
- If you did not personally inspect the output, say that explicitly
- Never use "✅" or "COMPLETE" for a step that was not verified
- If a claim was made in an earlier message and later disproved, correct it
  in a new message rather than quietly moving on

## Applies beyond screenshots

Same pattern for:

- **Data migration** — row counts in vs out, checksums on key columns,
  spot-check records at both ends
- **Batch file generation** — hash for duplicates, verify each opens
- **Bulk record writes** — read back a sample and compare to source
- **Deploys** — load the page after restart; do not infer from a clean log


## Second real example: the phantom missing file (2026-09-02)

The dashboard crashed. The agent reported `server.py` was missing — "the
directory exists but the server is gone" — and proposed restoring from backup.

None of it was true. There were **two directories with the same name**. The
agent checked one, found no `server.py`, and concluded catastrophic loss. The
real directory, with the file and full git history, was one path away. The
proposed restore would have been from a backup that did not even contain the
code.

This is the same failure as the screenshots: a confident conclusion reported
without the one check that would have disproved it — here, `ls` on both
candidate directories, or `find / -name server.py`.

**Before reporting anything missing, lost, or broken:**
- Search the whole machine, not one expected location (`find`, `locate`)
- Check for same-named files in sibling and parent paths
- Confirm the "backup" you propose actually contains what you think it does
- State what you checked, so the human can see the search was real

A false alarm about lost work is nearly as costly as the loss itself — it
triggers emergency recovery and erodes trust in every future report.

# VLS Deploy Safety

The VLS Command Center runs Victory Legal Solutions, Elektrica Rentals, and
Complete Collision. When it goes down, three businesses stop. A feature change
to titling took the entire system offline on 2026-09-01 and required a
whole-system rollback because the change could not be isolated.

This skill exists so that never happens again.

## The core rule

**Never edit production directly.** There must always be a gap between "code I
am working on" and "code customers are using."

## Required setup (do this before any other work)

If staging does not exist yet, building it is the highest-priority task —
ahead of every feature request.

1. **Two checkouts on the Mac mini**
   - `~/vls-staging/` — where all work happens. Break it freely.
   - `~/vls-production/` — only ever updated by promotion (below).

2. **Two ports, two tunnels**
   - Production keeps the existing Cloudflare tunnel and hostnames.
   - Staging runs on a separate port behind a separate hostname
     (e.g. `staging.elektricarentals.com`) or is reachable only on the LAN.

3. **Staging points at a copy of the data**, never at live data. A staging bug
   that writes to production records is the same outage by another route.

4. **Every promotion is a tagged git commit.** Rollback must be
   "check out the previous tag and restart," not "figure out what changed."

## The promotion checklist

Run through this every time. No exceptions for small changes.

- [ ] Change works in staging
- [ ] The specific screen or script that was touched has been loaded and exercised
- [ ] `python -c "import server"` succeeds — catches syntax and import errors
- [ ] All existing routes still resolve (smoke test, see below)
- [ ] Committed and tagged in git
- [ ] Promoted to production
- [ ] Production loaded and confirmed responding **after** restart
- [ ] If anything looks wrong: roll back first, diagnose second

## Smoke test

Before promoting, hit every top-level route in staging and confirm a 200.
A change to titling should not be able to break rentals, but on a monolith it
can — so check the whole surface, not just the part you touched.

Write this as a script (`scripts/smoke_test.py`) so it is one command, not a
habit someone has to remember.

## Rollback

Rollback should be one command and should take seconds:

```
cd ~/vls-production && git checkout <previous-tag> && <restart command>
```

**Roll back per change, not per system.** A whole-system rollback to an
arbitrary earlier point loses unrelated good work and makes it unclear what
state anything is in. If a single change broke production, revert that commit.

**Roll back before diagnosing.** Get the businesses back up, then investigate
in staging. Debugging under pressure with users offline is how small problems
become long ones.

## When something goes down

1. Roll back immediately
2. Confirm production is responding
3. Tell Jed what happened, in plain language, without waiting to be asked
4. Reproduce in staging
5. Fix, re-test, re-promote

Do not skip step 3. Jed finding out from a client is worse than any bug.

## Things that count as "production changes"

Not just `server.py`. All of these can take the system down:

- `static/index.html`
- Any cron job or automation script
- Database schema changes
- Dependency installs and upgrades
- Python version changes
- Cloudflare tunnel configuration
- Credential and token rotation

Each goes through staging first.

## What to never do

- Edit a file in production "just to test something"
- Restart production to see if that fixes it, before understanding why
- Deploy at the end of a session without confirming production came back up
- Report a change as complete without having loaded the page yourself

# VLS Domain Rules

Victory Legal Solutions: roughly 200 open cases, three people. The dashboard's
job is not to display data — it is to answer **"what is the most important
thing to do today, and what will break if nobody does it."**

Everything in this file exists to serve that question.

## Case types

Narrow by design. The case type plus the damage model IS the case summary —
do not build a free-text summary field that nobody will maintain.

| Type | Fee structure |
|---|---|
| Diminished value | Contingency |
| Unpaid repairs | Contingency |
| Rental | Contingency |
| Personal injury / negligence | Contingency |
| **First-party bad faith / DTPA** | **Fee-shifting** |

Add one optional free-text field, `unusual_notes`, empty by default. Because it
is normally empty, a filled one is a signal.

## First-party vs third-party — treat as top-level

This is not a label, it is a different business model on the same screen.

- **Third-party (contingency)**: our time is pure cost. Optimise for speed to
  settlement.
- **First-party (fee-shifting)**: our time is recoverable. Doing the work IS
  the value. **Unrecorded time is money not collected.**

Display this attribute everywhere a case appears — list, calendar, detail.
It feeds the priority score, not just the colour scheme.

Fee-shifting cases require time tracking. See "Time capture" below.

## Court event state machine

Every case carries `court_type` and `state`. The next expected event is a
function of both. Only two court types are in scope — hard-code them; do not
build a configurable rules engine for two rows.

### Pre-suit (bad faith / DTPA)

| State | Next expected event | Computed date |
|---|---|---|
| `intake` | Demand letter sent | — |
| `demand_sent` | 60-day notice period runs | `demand_sent + 60 days` = **earliest file date** |
| `notice_period_open` | Suit may be filed | Surface earliest-file-date, not just a deadline |

Store and display **the earliest date suit may be filed**, not only a deadline.
Filing early is as much a problem as filing late.

This phase currently lives only in the claims inbox and is untracked. It is the
highest-risk gap in the system: a missed statutory notice period can bar a claim.

### District court

| State | Next expected event | Computed date |
|---|---|---|
| `filed` | Service on defendant | — |
| `served` | Defendant's answer | Per rule |
| `answered` | Initial disclosures | `served + 30 days` |
| `discovery_open` | Discovery responses | Per service date of each request |

### JP court

| State | Next expected event | Computed date |
|---|---|---|
| `filed` | Service on defendant | — |
| `served` | Defendant's answer | Per rule |
| `answered` | **Motion for limited discovery must be filed** | — |
| `discovery_open` | Discovery responses | Per service date of each request |

JP is the easy one to get wrong: discovery is not automatic. After the answer,
a motion for limited discovery is required. A case sitting in `answered` in JP
with no motion filed is a stalled case, not a waiting one.

## Deadlines are computed, not typed

Do not ask an already-underwater human to type dates that follow from events.
Given a service date and a court type, the downstream dates are derivable.
Generate them.

The corollary: the system needs the **events**, and those are the fields that
currently go unentered.

## Missing data: make it visible, not mandatory

Do not add required fields. People type placeholder dates or skip creating the
record entirely, which is worse because the record then looks complete.

Instead, maintain a **blocked list** on the home screen:

> "14 cases cannot be scheduled — missing service date"

Every case with a filing date and no service date, or an answer with no next
event, appears here with a count. This doubles as the migration to-do list.

## Stalled cases

Any case sitting in one state past its expected window surfaces automatically —
without anyone remembering to check. With 200 files, the cases that hurt are
the quiet ones nobody has touched in six weeks, not the loud ones.

Also produce a weekly "cases that have not moved" list.

## Priority score

Three factors, multiplied:

1. **Hardness** — statutory bar date and trial rank far above a courtesy
   follow-up to an adjuster.
2. **Proximity** — how near the deadline is.
3. **Work remaining** — a task due Friday needing eight hours is more urgent
   *today* than a ten-minute task due Wednesday.

Modifiers:

- Fee-shifting cases: doing the work is billable, weight accordingly
- Client-caused delay (unreturned discovery, treatment gap): raise priority
- Blocked on missing data: surface separately, do not silently rank low

### Jed's stated hierarchy

**Highest** — the discovery chain: filed → served → answered → disclosures →
our discovery out → theirs in → responses due.
**Also high** — trials, mediations, depositions.
**Lower** — response from opposing counsel on an offer; adjuster response.

## Personal injury: treatment gaps

Treatment gaps directly reduce settlement value, so this makes money.

Each PI case carries an expected treatment cadence (e.g. weekly, fortnightly).
**Silence is the signal** — if nothing is logged past the window, surface
"possible treatment gap" and raise priority automatically. Do not rely on the
client remembering to log; a client who has stopped treating is exactly the
client who has stopped logging in.

Logging must be one tap: date and provider, nothing more.

## Medical bills

Medical totals feed the damage model, which sets case value. Handle carefully.

- Bills arrive in the claims inbox. A bot extracts provider, date, amount.
- **Every entry stores provenance**: source email message ID, date, provider.
  Without the link, reconciliation is guesswork and the figure is not
  defensible in litigation.
- Auto-extracted entries are marked **unconfirmed**. The case shows both
  totals — confirmed and pending. Never send a demand on unconfirmed figures.
- Monthly automated request to each provider on file for an updated balance;
  responses update the record.
- Providers who have gone quiet surface, same silence-as-signal pattern.

## Email-driven capture

All firm email forwards into the claims inbox — one place, attached to cases.

The bot **proposes, never decides**. Adjusters write ambiguously, sometimes
deliberately. A misread that silently downgrades a case is invisible until it
is not. So: "this looks like a settlement offer — raise priority?" with a human
clicking yes. Same speed, no silent failure.

## Time capture

Do not build a stopwatch. Nobody remembers to press start.

Log time from actions already being taken: send an email from the dashboard,
log an entry. Draft a motion, log it. Pre-fill a suggested duration and
description; the user adjusts or accepts.

End-of-day nudge: "here is what you did, here is what is logged, anything
missing?" Reconstruct rather than capture live.

## Intake: match before create

Signed engagement letters arrive via Adobe or JotForm. Do not create a case
blindly.

1. Match on phone and email
2. Then name and date of birth
3. **Exact match** → attach to existing case
4. **Close match** → queue as "possible duplicate" for human confirm-or-split
5. **No match** → create new

Never auto-merge on fuzzy name matches. Two clients' records fused together is
far worse than a duplicate. Store `intake_source` (adobe / jotform / manual) on
every case.

## Client portal scope

Build the **read-only half first**. Status, what was filed, what we are waiting
on, what is next. This deflects calls and costs nothing ongoing.

Then client tasks: assigned discovery with a due date, automated nudge, upload
back to the case, auto-marked done. "Waiting on client" becomes a countable state.

**Buffer client-facing deadlines.** If responses are due to opposing counsel on
the 20th, tell the client the 15th. Clients are late and you need review time.

Hold the free-text messaging channel until read-only status has been tried. A
chat channel is a new inbox someone has to staff — it adds work rather than
removing it.

# VLS Data Model & Migration

## Why we are moving off Sheets

Google Sheets has no transactions and no concurrency control. Kay has confirmed
this has already caused silent data corruption — rental sync race conditions and
payment tracking overwrites. Automation scripts write on cron schedules while
users write through the UI, and bots write faster and more often than people.

Legal case data carrying statutory deadlines cannot tolerate lost updates.

**Target: PostgreSQL**, managed (Supabase or Neon, roughly $25/month) so the
data lives off the Mac mini with continuous backup and point-in-time recovery.

SQLite would fix correctness for free but keeps everything on one box. Given
bots writing concurrently and three businesses depending on it, go to Postgres.

Note: the app can continue running on the Mac mini for now. Data safety and
uptime are separate problems; data is the one that cannot be undone.

## Migration order

**Database → server modularisation → frontend.** Last, not first.

Rebuilding a 43,000-line frontend on top of Sheets relocates the problem rather
than fixing it. The frontend is ugly and hard to extend, but it works. The data
layer is the thing that can silently lose a deadline.

## Schema conventions

### Every table

- `id` — surrogate primary key
- `created_at`, `updated_at` — timestamps, not optional
- `created_by`, `updated_by` — human user or named bot

### Provenance on anything a bot writes

Any record produced by extraction from email or an external API stores where it
came from:

- `source` — e.g. `claims_inbox`, `adobe`, `jotform`, `manual`, `black_book`
- `source_ref` — email message ID, envelope ID, API record ID
- `extracted_at`

Without provenance, reconciliation is guesswork and figures are not defensible.

### Confirmed vs unconfirmed

Anything a bot proposes carries `confirmed` (boolean) and `confirmed_by`.
Aggregates must be able to report both totals separately — e.g. medical bills
show confirmed total and pending total. Nothing goes into a demand unconfirmed.

### Events, not just state

Case state is derived from an append-only `case_events` table
(`case_id`, `event_type`, `event_date`, `source`, `source_ref`, `notes`).

Storing only current state loses the history that computed deadlines depend on,
and makes it impossible to answer "when did this actually happen." Deadlines are
computed from events; the state column is a cached read of the latest event.

### Dropdowns over free text

Case type, court type, event type, state — all constrained. Free text goes
stale and cannot be queried. The one deliberate exception is `unusual_notes`,
empty by default.

## Normalising ~50 Sheets tabs

Design the schema **fresh from the domain**, then map legacy data onto it. Do
not transliterate tabs into tables — the tab structure reflects what was easy in
Sheets, not what the domain actually is.

Export all tabs to CSV/JSON first for analysis, then write the mapping
explicitly, column by column, in a file that can be reviewed.

## Migrating without losing information

The honest constraint: **much of what the new system needs was never captured.**
Service dates, court type, case state, first-party flag — these are new. You
cannot migrate what does not exist.

So:

1. Move what exists
2. Let every case land with its gaps **visible** — the blocked list becomes the
   migration to-do list ("14 cases missing service date")
3. Chip away, a few minutes per case, rather than one heroic weekend
4. Where possible, backfill from the claims inbox — service confirmations and
   answers are in email; propose values for one-click human confirmation

### Verify the move

Row counts in vs out. Checksums on money columns. Spot-check records at both
ends. See the `verify-before-done` skill — a migration that reports success
while dropping rows is the worst possible failure mode here.

## Parallel running

Nothing gets turned off until the new system is proven.

- New database becomes source of truth
- Keep Sheets as a **read-only** reporting view during transition — do not cut
  it off, but stop writing to it
- Run both, compare, and only then retire the old path

## Features to preserve

Do not lose these in migration. They work and they are used daily:

- **Financials tab** — case costs, award, attorney's fees, and one-button PDF
  settlement breakdown generation. Keep the whole flow.
- **Medicals tracking** — must link to the damage model and to provenance
- The 100+ automation scripts — inventory them before the cutover; each one
  writing to Sheets needs a new target

## Security note

Credentials do not belong in files stored in shared Drive folders, in git, or
in messages. A live password was pasted into `KAY_TO_CLAUDE_001.md` on
2026-09-01 — rotate it. Use environment variables or a secrets file that is
gitignored.

Password reset is currently manual (editing a sheet). Address authentication
early in the migration rather than carrying it forward.

## Client confidentiality

The Drive folder currently holds screenshots containing client names, phone
numbers, a claim number, court correspondence and Zoom links. Use seeded or
demo data for any future captures, and clear out real-data artifacts once
reviewed.

## 3. Architecture decisions — APPROVED

### ADR-001 — Option C (approved, conditional)
Three **separately deployable apps** (VLS, Elektrica, Collision) on **one managed Postgres** with **three schemas** plus a **small shared platform schema**, and a shared library holding conventions and primitives only.

Reasoning that carried it: the 2026-09-01 outage (a titling change took down all three businesses) is a structural property of a single process, not a bug. Only a process boundary fixes it. Per-app tag sequences make "roll back per change, not per system" mechanical.

**Hinge condition (binding):** the platform schema holds identity and cross-cutting infrastructure only — never domain lifecycle. No state machines, no deadlines, no money, no matter/order/booking attributes. Operational test: *does a change to one business's domain force a platform migration?* If it ever does, the boundary is violated and the modular monolith becomes the safer structure.

**Platform schema migrations:** additive-only, backwards-compatible, both shapes tolerated for one release. This is the one place a change can still reach all three apps.

**Build order:** VLS first, alone. Extract `_shared` only when a second consumer actually needs a piece of it. Extracting before there's a second consumer produces an abstraction shaped by one use case.

**Operational burden:** three pipelines should be one template stamped three times, and Jocasta runs them, not the humans.

### ADR-002 — Identity / shared person registry (approved, with RLS condition)
- `platform.person` is deliberately thin: names, DOB, normalised contact points. Nothing else.
- Each app owns its own party table keyed by `person_id`: `vls.client` (engagement date, fee structure), `collision.customer` (vehicle ownership), `elektrica.renter` (licence, deposit).
- The registry does **not** record which businesses a person is involved with. The fact of legal representation lives only in `vls.client`.
- **Row-level security is required on `platform.person`:** each app reads only rows linked from its own party table. A VLS-only client is invisible to Collision and Elektrica — not hidden, invisible. Without this, a Collision employee could find a name that exists in the system only because the person is a firm client.
- Identity resolution at intake runs with platform-level privilege as a single trusted, logged service — not a per-app query. Jocasta to argue where it lives.
- Merges are append-only and reversible via `platform.person_merge`.
- Conflict checking stays inside VLS, since only VLS can answer it.

### Customer overlap — confirmed YES, structural
One car accident routinely produces a VLS client (diminished value, unpaid repairs, rental-reimbursement claim), a Complete Collision repair order, and an Elektrica rental — often the same person in the same month. This is the business model. It does NOT flip the recommendation to a single platform: overlap in *people* is not overlap in *domain objects*. Shared person, separate domain objects.

### Austin Legal — NOT a fourth business
`austinlegal.elektricarentals.com` is a second, partial VLS dashboard Jed started building (4 sections, own login, own client data). It is a **second legacy data source for the VLS migration**, not a business. No schema for it. Migration plan must handle two sources (Command Center sheets + Austin Legal sheets), possible overlap between them, match-before-create across both.

## 4. VLS schema — APPROVED (commit 2aa977c, verified 32/32 against Postgres 16.15)

Present and behaviourally proven:
- `case_event` append-only (DELETE denied, history UPDATE denied, confirmation UPDATE allowed)
- State derived from events, never typed
- `court_type` constrained to JP / District; JP `answered` → `motion_limited_discovery_filed`; District `answered` → `initial_disclosures_due`
- `demand_sent` + 60 → earliest file date (function to be renamed from `computed_deadline` to `earliest_file_date` — approved, pending)
- Provenance (`source`, `source_ref`, `confirmed`) enforced; an extracted medical bill without `source_ref` is rejected
- Blocked list expressible as a query ("filed but no service date")
- Financials (`003_vls_financials.sql`): `case_cost` itemised with `recoverable` flag; `case_financial` one row per case with fee split, `fees_sought` and `fees_awarded` separate; reconciliation required only on resolved cases

Approved next steps, in order: rename → land RLS as migration 004 (the test assertion that "zero RLS policies exist" then flips) → make the verification harness permanent as `scripts/verify_schema.sh` → fixtures.

## 6. Security findings from the audit of the CURRENT system — design requirements for the NEW one

Kay audited `server.py` on 2026-09-02. Findings that must shape the new build:

1. **The localhost guard has never held.** `cloudflared` on the mini forwards every request to `localhost:5150`, so every internet visitor arrives as `127.0.0.1`. Every "localhost-gated" route — deadlines summary, warranty, email-intel, jed-notes — has been public. A curl from the cloud box returned named clients and overdue counts unauthenticated.
   → **New system: never trust `remote_addr`. Auth is a property of the route, not of where the request appears to come from. Real client IP comes from `CF-Connecting-IP` and is logged, not trusted for auth.**

2. **The auth allowlist is the exposure.** A global `before_request` gate blocks everything by default, but an allowlist of prefixes bypasses it. Mistakenly open: `/api/vls/cases`, `/api/vls/fax-demand` (send faxes as the firm), `/api/summary` (firm-wide financials), `/api/warranty/`, and the `/api/cc/` wildcard. Legitimately public because customer-facing sites call them: payment intents, portal, shared links.
   → **New system: default-deny, and every public route is an explicit, individually justified exception with its own reason recorded in code. No prefix wildcards in an allowlist. CORS is not auth.**

3. **API-key auth already exists** (`X-API-Key` / `?api_key=`, `_authenticate_api_key()`). Automations should use it; nothing should rely on localhost.
   → **New system: service-to-service calls authenticate with scoped keys from day one. Each automation gets its own key so a leak is attributable and revocable.**

4. Secrets were found in plaintext in config files, in Drive documents, and pasted into chat windows three times in two days.
   → **New system: secrets in environment or a secrets store, never in config committed anywhere, never in chat. `verify-before-done` applies to "is this secret somewhere it shouldn't be."**

5. The immediate patch to the *existing* system (Kay writing, Jed applying on the mini per deploy-safety): remove the localhost bypass; split the allowlist into justified-public vs mistaken; remove the mistakes; log `CF-Connecting-IP`; include the rollback command. Jed to check Cloudflare request logs for prior hits on the exposed paths.

## 7. Verification standard — reaffirmed with today's evidence

Three times today an agent reported a conclusion that was not verified: the "missing" `server.py` (wrong directory), "the server is live and writing" (inferred from timestamps, no process running), and "117 unauthenticated routes" (decorator scan missed a global gate; real number ~40). Jocasta caught herself three times reporting green from a superseded run.

The standard, restated: **report what you confirmed and how you confirmed it. Evidence from the committed state, not the working tree. If you didn't inspect the output, say so. A false alarm about lost work costs nearly as much as the loss.**

Jocasta's honest framing is the model: "self-authored tests on self-authored code catch internal inconsistency but can't catch a misunderstanding of Texas practice. Only Jed can check that part."
